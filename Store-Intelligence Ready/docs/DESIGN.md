# DESIGN.md - Store Intelligence System

> **Purplle Tech Challenge 2026 — Round 2 Submission**

---

## 1. Project Overview

Store Intelligence is an end-to-end computer vision and retail analytics pipeline built to process raw CCTV footage, detect human movement, and translate visual signals into actionable business metrics. The core objective is to derive reliable telemetry — conversion rates, queue depth, funnel analytics — from ambiguous, noisy visual data while respecting real-world constraints such as edge hardware limitations at retail locations.

Rather than treating this as a model-building exercise, the system is engineered as a robust data pipeline. Every design decision prioritises determinism and edge deployability over theoretical scalability.

The system is designed around an **event-driven architecture**: every observable action in the store (a person entering, dwelling in a zone, joining a billing queue) is converted into a structured, schema-validated JSON event. These events are the single source of truth for all downstream analytics.

## 3. High-Level Architecture

The system employs a strictly decoupled, four-stage pipeline architecture:

```text
[CCTV Video (.mp4)] — 4 cameras per store
         │
         ▼
┌──────────────────────────────────────────┐
│           Detection Pipeline             │
│  CLAHE Pre-processing                    │
│  YOLOv8m · ByteTrack · OSNet             │
│  Shapely Zone Mapping · Staff Detection  │
│  Output: raw .jsonl event files          │
└──────────────────────────────────────────┘
         │
         ▼  (Batch POST — up to 500 events)
┌──────────────────────────────────────────┐
│           Intelligence API               │
│  FastAPI (async) · SQLite (aiosqlite)    │
│  Ingest · Metrics · Funnel · Anomalies   │
└──────────────────────────────────────────┘
         │
         ▼  (3-second HTTP polling)
┌──────────────────────────────────────────┐
│           Live Dashboard                 │
│  Vanilla JS / HTML — No build step       │
│  KPI cards · Funnel · Heatmap · Alerts   │
└──────────────────────────────────────────┘
```

### Camera Layout (4 Cameras per Store)

Each store is covered by 4 primary camera angles:

| Camera Role | Coverage Area | Primary Responsibility |
|---|---|---|
| **Entry Camera** | Front door / Entry threshold | `ENTRY` / `EXIT` / `REENTRY` event emission |
| **Zone Camera 1** | Main floor — primary product zone | Zone dwell tracking for product categories |
| **Zone Camera 2** | Main floor — secondary product zone | Zone dwell tracking for product categories |
| **Billing Camera** | Billing counter — queue view | `BILLING_QUEUE_JOIN` / `BILLING_QUEUE_ABANDON` |

The entry camera is the authoritative source for session creation. The floor cameras cover specific product zones (e.g. Makeup, Skincare). OSNet maintains Re-ID continuity when visitors transition between these cameras.

The heavy GPU-bound inference pipeline runs outside Docker to avoid GPU-passthrough penalties on Windows edge hardware. The API and database run inside Docker Compose.

## 3. Detection Pipeline

### Pre-Processing

**CLAHE** (Contrast Limited Adaptive Histogram Equalisation) is applied per-frame before detection to normalise lighting variation between natural sunlight and fluorescent lighting — a real-world issue in retail environments where ambient light shifts across a 20-minute clip.

### Person Detection

The pipeline uses **YOLOv8m** with pre-trained COCO weights (zero-shot approach). The sole detection class required is `person`. Each detected bounding box is passed through four sequential handlers:

1. `zone_mapper.get_zone()` — Shapely point-in-polygon check for zone assignment
2. `staff_classifier.classify_staff()` — HSV torso analysis for uniform detection
3. `tracker.update()` — ByteTrack MOT and OSNet Re-ID assignment
4. `emit.emit_event()` — Pydantic schema validation and `.jsonl` write

### Group Entry Handling

Group entries are handled intrinsically by YOLO's Non-Maximum Suppression (NMS). NMS identifies distinct, non-overlapping bounding boxes for individuals walking shoulder-to-shoulder, ensuring that 3 people entering together produce 3 separate bounding boxes and therefore 3 separate `ENTRY` events — preventing artificial deflation of visitor counts.

### Occlusion and Confidence Calibration

Rather than silently dropping bounding boxes when a person is partially obscured by retail shelving, the pipeline takes two explicit steps:

1. **Confidence preservation:** Every emitted event includes the raw `confidence` score from the YOLOv8 detection head. Low-confidence detections are never suppressed — they are emitted with their score intact so the API layer can apply threshold filtering independently if needed. A `confidence=0.2` event is stored and served; dropping events would lose information needed for calibration.
2. **Trajectory momentum via ByteTrack:** When a person steps behind a shelf and confidence drops below the primary detection threshold, ByteTrack holds the track in a secondary low-confidence buffer rather than terminating the `visitor_id`. This prevents a single person reappearing from behind a shelf from being counted as a new visitor.

### Staff Detection

Staff members are identified at the pipeline level using HSV colour-space thresholding applied to the torso region of each bounding box, targeting known uniform colours (e.g. purple torsos for Apex Retail staff). Events from detected staff are immediately flagged `is_staff: true` and excluded from all session creation and customer metric calculations. All API queries explicitly filter `WHERE is_staff = 0`.

We evaluated using a Vision Language Model (VLM) for staff detection but chose HSV thresholding instead — it is fully deterministic, requires no API calls at inference time, and performs reliably given that staff uniforms have consistent, distinct colours across all store footage.

## 4. Tracking and Re-Identification

### Intra-Camera Tracking (MOT)

**ByteTrack** handles Multi-Object Tracking within a single camera's field of view via the built-in `ultralytics` ByteTrack integration. Its key advantage over DeepSORT in retail environments is its two-buffer approach: high-confidence detections are tracked normally, while low-confidence detections (e.g. a person half-hidden behind a display stand) are held in a secondary buffer and re-associated rather than dropped. This prevents broken track IDs in crowded aisles — the primary failure mode of DeepSORT in this setting.

### Cross-Camera Re-Identification

**Torchreid OSNet (`osnet_x1_0`)** handles cross-camera identity association using pre-trained weights. When a visitor moves from one camera's field of view into another's, OSNet computes an appearance embedding from the bounding box crop and compares it against recently-active session embeddings using cosine distance. If the distance is below **0.4** within a **5-minute window**, the same `visitor_id` is reused — ensuring the same physical person is not counted twice across camera boundaries.

OSNet was chosen over FastReID specifically because of its omni-scale feature learning — it captures features at multiple spatial scales simultaneously, which is critical given that the CCTV cameras have varying focal lengths and capture subjects at different apparent sizes.

The 0.4 distance threshold and 5-minute window were chosen empirically to distinguish brief exits (phone calls, quick breaks outside) from genuine same-day return visits.

**Known limitation:** OSNet can fail when a visitor's clothing is highly generic (plain black top, dark jeans) under variable fluorescent lighting. In these cases the Re-ID confidence drops and the system may fragment the session into two partial tracks. We accept this tradeoff in exchange for real-time inference speeds on edge hardware.

### Re-Entry Handling

If a visitor exits the store and returns, OSNet matches their appearance embedding to the existing `visitor_id`. Rather than opening a new session (which would inflate `unique_visitors`), the system emits a `REENTRY` event and increments the `reentry_count` field on the existing session. The funnel uses `COUNT(DISTINCT visitor_id)` — not `COUNT(*)` — ensuring re-entries never inflate funnel stage counts.

## 5. Event Generation Logic

The pipeline uses the **Shapely** geometry library to map dynamic bounding box coordinates into static polygonal zones defined in `store_layout.json`. When the centroid of a bounding box intersects a zone polygon, the pipeline evaluates the visitor's state and emits the appropriate typed event.

**Timestamps** are computed as: `clip_start_time` (from `store_layout.json`) + `frame_number / fps` seconds. This ensures timestamps are deterministic and reproducible regardless of when the pipeline runs.

### Event Type Catalogue

| Event | Trigger |
|---|---|
| `ENTRY` | Bounding box crosses entry threshold polygon inbound |
| `EXIT` | Bounding box crosses entry threshold polygon outbound |
| `REENTRY` | Previously exited `visitor_id` re-detected at entry threshold |
| `ZONE_ENTER` | Centroid enters a named zone polygon |
| `ZONE_EXIT` | Centroid leaves a named zone polygon |
| `ZONE_DWELL` | Visitor present in zone continuously for 30+ seconds (emitted every 30s) |
| `BILLING_QUEUE_JOIN` | Visitor enters billing zone while queue depth > 0 |
| `BILLING_QUEUE_ABANDON` | Visitor leaves billing zone without a subsequent POS match |

### Camera Overlap Deduplication

With multiple cameras covering the same physical store, overlap zones are inevitable — particularly between the entry and the main floor cameras. The pipeline enforces a geometric suppression rule: `ENTRY` and `ZONE_ENTER` events emitted from a secondary camera inside an overlap polygon (as defined in `store_layout.json`) are dropped in favour of the primary camera.

Priority order typically enforces: Entry > Primary Zone > Secondary Zone > Billing within their respective coverage overlaps. This prevents the same physical crossing from generating duplicate events across cameras.

## 6. Session Management

A **Visitor Session** is the logical container for a visitor's complete in-store journey. The three tables backing sessions are `events`, `visitor_sessions`, and `pos_transactions`.

- **Open:** A session is strictly opened when a visitor crosses the `ENTRY_AREA` polygon threshold in the inbound direction on `CAM_ENTRY_01`, triggering an `ENTRY` event. A new `visitor_id` (UUID v4) is assigned.
- **Close:** A session closes on an `EXIT` event or when the visitor has not been detected across any of the cameras for longer than the session timeout window.
- **Re-entry:** Returning visitors do not open new sessions. Their existing session is updated with a `REENTRY` event and an incremented `reentry_count`.
- **Staff filtering:** Events flagged `is_staff: true` never trigger session creation and are excluded from all customer-facing metrics via `WHERE is_staff = 0` on every query.

## 7. Backend and API Design

The backend is built with **FastAPI**, leveraging Python's `asyncio` for non-blocking I/O. The primary bottleneck is SQLite disk I/O, so async endpoints allow the server to handle concurrent dashboard reads while batch writes are in progress.

### Batch Ingestion

The `POST /events/ingest` endpoint accepts payloads of up to **500 events per request**. This serves two purposes: it reduces transaction commits against SQLite (mitigating write-lock contention), and it allows the pipeline to catch up quickly after processing a backlog of frames across all cameras.

**Idempotency:** The endpoint is safe to call multiple times with the same payload. Each event carries a globally unique `event_id` (UUID v4). Deduplication is enforced at the database layer via a `UNIQUE` constraint on the `event_id` column — duplicate inserts are silently ignored using `INSERT OR IGNORE` semantics. Running `ingest_new_data.py` twice with the same `.jsonl` files produces identical metric outputs.

**Partial success:** If a batch of 500 events contains 3 malformed events, the 497 valid events are committed and the 3 failures are returned in a structured error body. The entire batch is never rejected because of a minority of bad events.

### POS Correlation

A background `asyncio` worker runs on a short polling interval and stitches POS transactions to active visitor sessions. The correlation rule: a visitor who was present in the billing zone (`CAM_BILLING_01` coverage) at any point within the **5-minute window before a POS transaction timestamp** is counted as a converted session for that transaction. Because the POS data contains no `customer_id`, time-window proximity within the billing zone is the sole correlation signal.

### Graceful Degradation

All database operations are wrapped in structured exception handlers. A global FastAPI exception handler catches `sqlalchemy.exc.OperationalError` and all unhandled exceptions, returning structured error responses — never raw Python tracebacks. If SQLite becomes unavailable, the API returns:

```json
{
  "error": "SERVICE_UNAVAILABLE",
  "detail": "Database is temporarily unavailable. Retry after 5 seconds.",
  "status_code": 503
}
```

## 8. Database Design

We explicitly chose **SQLite** (via the `aiosqlite` async driver) over PostgreSQL or Redis.

Retail stores operate as edge environments — typically a backroom PC with constrained RAM, no guaranteed network uptime, and a single operator who cannot manage database containers. Deploying a PostgreSQL + Redis stack introduces multiple points of failure and demands persistent container management. SQLite keeps the entire database as a single portable file (`store_intelligence.db`), making it trivially easy to back up, inspect, and redeploy.

SQLite's known weakness — poor concurrent write performance due to database-level locking — is mitigated by the 500-event batch ingestion design. Rather than many small individual writes, the system commits infrequently in large atomic batches, dramatically reducing lock contention.

The tradeoff accepted is that the system cannot horizontally scale across multiple API instances. For a single-store edge deployment, this is not a constraint.

## 9. Metrics Computation

All metrics are computed entirely on-the-fly using raw SQL aggregations (`sqlalchemy.text`). No pre-computed state is maintained, which eliminates drift between stored values and actual event data.

- **`queue_depth`:** `MAX(0, COUNT(BILLING_QUEUE_JOIN) - COUNT(BILLING_QUEUE_ABANDON or EXIT))` over the current active billing zone window.
- **`conversion_rate`:** `converted_sessions / total_sessions` where a converted session has a matched POS transaction within the 5-minute billing window.
- **`abandonment_rate`:** Fraction of sessions that triggered `BILLING_QUEUE_JOIN` but closed without a matched POS receipt.
- **`avg_dwell_per_zone`:** Average `dwell_ms` aggregated by `zone_id` across all non-staff sessions in the query window.

Raw SQL is used directly rather than an ORM. This increases query verbosity but gives full control over the aggregation logic and avoids ORM translation overhead on latency-sensitive endpoints.

## 10. Anomaly Detection

Anomaly detection runs as an intermittent background task and surfaces alerts with structured severity levels. Each anomaly includes a `suggested_action` string for on-call operators.

| Anomaly | Condition | Severity | Suggested Action |
|---|---|---|---|
| `STALE_FEED` | Time since last event from any of the cameras > 10 minutes | `CRITICAL` | Check camera connectivity and pipeline process |
| `BILLING_QUEUE_SPIKE` | `queue_depth` exceeds configured store capacity threshold (default: 5) | `WARN` | Open additional checkout counter |
| `CONVERSION_DROP` | Current conversion rate < 7-day rolling average by more than 15% | `WARN` | Review funnel drop-off zone and staffing |
| `DEAD_ZONE` | Named zone has received zero visits in the past 30 minutes during open hours | `INFO` | Check camera coverage for that zone |

The 7-day rolling average for `CONVERSION_DROP` is computed by aggregating historical session data from the past 7 days using a windowed SQL query on the `visitor_sessions` table, run at each anomaly check interval.

`STALE_FEED` is checked per camera — a single camera going offline triggers a `CRITICAL` alert rather than waiting for all cameras to go dark.

## 11. Real-Time Communication and Dashboard

Two dashboard implementations are provided:

**Terminal dashboard** (`dashboard/terminal_dashboard.py`): Uses `rich.live.Live` for in-place terminal rendering. Polls metrics every 3 seconds, anomalies every 10 seconds, and health every 15 seconds. Severity-coloured anomaly display (`INFO`=blue, `WARN`=yellow, `CRITICAL`=red). Handles API offline gracefully without crashing.

**Web dashboard** (`dashboard/web/index.html`): A Vanilla JS / HTML / CSS single-page application served as a static file directly from the FastAPI server — no separate frontend container, no build step. Uses a **3-second HTTP polling cycle** via the native `fetch` API.

Rather than implementing WebSockets (which would require managing persistent connection state for every connected client on the FastAPI server), the frontend polls on interval. Business metrics like conversion rate and queue depth are macro-level figures that do not require sub-second precision — a 3-second cycle provides near-real-time perception with zero backend state management overhead.

The dashboard renders: live KPI cards (visitors, conversion rate, queue depth), a zone dwell heatmap (visit frequency and avg dwell normalised 0–100), a conversion funnel (Entry → Zone Visit → Billing → Purchase), and active anomaly alerts with severity badges.

## 12. Production Readiness

### Structured Logging

Every API request produces a structured JSON log line containing: `trace_id` (UUID per request), `store_id`, `endpoint`, `latency_ms`, `event_count` (ingest endpoints only), and `status_code`. This makes logs directly queryable by any log aggregation tool without parsing free-form text.

### Idempotency

`POST /events/ingest` is safe to call multiple times with identical payloads. Deduplication is enforced at the database layer via a `UNIQUE` constraint on the `event_id` column using `INSERT OR IGNORE` semantics. This also means the pipeline can replay `.jsonl` files safely after a crash without corrupting metrics.

### Graceful Degradation

A global FastAPI exception handler catches `sqlalchemy.exc.OperationalError` and all unhandled exceptions, returning structured error responses with appropriate HTTP status codes. Raw Python tracebacks are never exposed in API responses.

### Schema Validation

Incoming events are validated against strict Pydantic models in `app/models.py` before any database write. Events missing required fields, containing malformed timestamps, or carrying out-of-range confidence scores are rejected with a structured error body. Valid events in the same batch are committed regardless.

### Testing Strategy

The test suite targets >70% statement coverage and is organised around the specific edge cases in the challenge footage:

- **Empty store periods:** API correctly returns zero-value metrics without crashing or returning null.
- **All-staff clip:** Conversion rate returns `0.0` with `unique_visitors: 0` since all sessions are filtered.
- **Zero purchases:** `conversion_rate` returns `0.0`, not a divide-by-zero error.
- **Re-entry in funnel:** A `REENTRY` event does not create a second funnel entry for the same `visitor_id`.
- **Idempotency:** `POST /events/ingest` called twice with identical payload produces identical metric output.
- **Partial occlusion events:** Low-confidence events are stored and served — not silently dropped.

## 13. AI-Assisted Decisions

Generative AI was used extensively during prototyping and selectively overridden during production hardening.

**Adopted — Schema bootstrapping:** AI generated the initial Pydantic event schema models covering all required fields (`event_id`, `visitor_id`, `zone_id`, `dwell_ms`, `is_staff`, `confidence`, `metadata`). This was adopted with minor adjustments and saved several hours of boilerplate work.

**Adopted — Synthetic test data:** AI generated a realistic synthetic `pos_transactions.csv` with appropriate timestamp distributions and basket value ranges for testing POS correlation logic. Required minor adjustments to align timestamps with session windows in the test clips.

**Adopted — Docker Compose:** AI produced the initial `docker-compose.yml` for the FastAPI service and volume mounts. Adopted with modifications to remove unnecessary services it added by default.

**Overridden — Infrastructure stack:** AI consistently recommended Kubernetes + PostgreSQL + Redis for "production scalability." I explicitly rejected all three. The deployment target is a retail back-office PC, not a cloud VM. Kubernetes on backroom hardware would make deployment impossible for a non-DevOps store operator. I forced the architecture to Docker Compose + SQLite, accepting the horizontal scalability tradeoff in exchange for one-command deployability.

**Overridden — Detection model:** AI suggested building a custom ResNet-based detection model trained on store-specific footage. I rejected this because it requires a large proprietary labelled dataset, a training pipeline, and ongoing retraining as store layouts change. Pre-trained YOLOv8m delivers equivalent accuracy for the `person` class at zero data cost.

**Overridden — Real-time communication:** AI recommended WebSockets for the dashboard. I rejected this in favour of 3-second HTTP polling. WebSockets add server-side connection state management with no meaningful accuracy benefit for macro-level business metrics.

**Overridden — Re-ID approach:** AI initially suggested using bounding box trajectory as the primary Re-ID signal. I weighted OSNet embedding distance more heavily instead, because trajectory alone breaks when two people enter from the same direction 3 seconds apart — a scenario explicitly flagged in the challenge problem statement as an edge case.

## 14. Limitations

1. **Lighting and OSNet fragmentation:** Severe lighting changes (e.g. direct sunlight shifting over 20 minutes) significantly degrade OSNet embedding quality, occasionally causing the same visitor to receive two separate `visitor_id` values across camera boundaries. This inflates `unique_visitors` slightly and deflates `conversion_rate` correspondingly.

2. **Eventual consistency:** The detection pipeline processes frames in chunks and pushes batches asynchronously. The live dashboard lags reality by approximately 3–5 seconds during high-traffic periods. This is acceptable for macro-level business metrics but would not suit real-time alerting at the individual event level.

3. **Hardware dependency:** YOLOv8m requires a dedicated NVIDIA GPU for real-time 15fps inference across 4 cameras. On CPU-only edge devices the pipeline falls back to YOLOv8n (nano), trading roughly 15–20% bounding box accuracy for deployability.

4. **Queue abandonment lag:** `BILLING_QUEUE_ABANDON` is emitted only after a 10-minute inactivity timeout. If a visitor walks away from the billing queue without triggering a clean `EXIT`, `queue_depth` temporarily over-reports until the timeout fires.

5. **Single-store scalability ceiling:** SQLite's single-writer model means the current architecture cannot support multiple pipeline instances writing to the same database simultaneously. A multi-store cloud deployment would require migrating to PostgreSQL and revisiting the batch ingestion design.

## 15. Future Improvements

1. **TensorRT / ONNX export:** Replacing the PyTorch YOLOv8 runtime with a TensorRT-optimised ONNX model would dramatically improve frames-per-second across all camera feeds on edge hardware and remove the NVIDIA-only constraint.

2. **3D Homography mapping:** Transitioning from 2D Shapely polygon intersection to a full projective homography matrix per camera would allow all camera feeds to be mapped onto a unified top-down floor plan, eliminating the manual overlap suppression rules and enabling precise visitor path reconstruction.

3. **Exponential moving average queue prediction:** Upgrading `queue_depth` from a raw count to an EMA-smoothed metric would enable wait-time estimation rather than just current depth reporting.

4. **Online Re-ID fine-tuning:** Periodically fine-tuning OSNet embeddings on store-specific staff uniform negatives would reduce false Re-ID matches and improve cross-camera session stitching accuracy across the multi-camera setup.

5. **Per-camera anomaly granularity:** Currently `STALE_FEED` is raised at the store level. A future improvement would surface which specific camera among the cameras is stale, enabling faster diagnosis by on-call operators.
